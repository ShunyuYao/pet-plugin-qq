# 吐梨邦 QQ 插件：产品模式、后端配置与优先级

更新日期：2026-11-02。`pet-plugin-qq` 是 **吐梨邦桌宠的 QQ 连接插件**，通过吐梨邦的插件系统安装和运行。本文中的“桌宠”和“宿主”均指吐梨邦，使用本插件需要配合兼容的吐梨邦版本。

本文记录两种模式及其优先级；当前安装步骤见 [README](../README.md)，历史实现证据见 [0.1.0 交付记录](v1-delivery.md)。

## 已确认的产品决定

用户于 2026-11-02 明确要求：项目说明必须清楚标明这是吐梨邦的插件。仓库简介、README 和产品说明均应保留这一产品归属。

用户于 2026-11-02 明确：

> 这两个肯定都要做的，而且其实第一个应该更优先一些。

对应本轮讨论中的两个模式：

1. **模式一：让当前桌宠接入 QQ。首要必做，后续开发优先。** 复用用户正在使用的桌宠模型配置、人设、会话和记忆，用户无需为了 QQ 聊天另外安装完整 DSH 服务。
2. **模式二：连接已有 QQ 宠物。同样必做。** 保留原宠物的历史、人设和记忆，让桌面成为它的另一个入口；不能用新建一只空宠物替代。

两种模式都要满足“QQ 和桌宠是同一只宠物，两边能接着聊”。“必做”指产品必须提供这两种能力，用户按自己的情况选择，并非要求每个人同时启用两种模式。

本决定更新了此前“先接已有 DSH 宠物”的开发顺序。已完成的 DSH 适配继续保留，但不能据此把模式一降为可选扩展，也不能把 DSH 作为所有用户的强制依赖。

用户此前确认的 **B 站生活联动可选、不强制** 继续有效：两种模式的核心聊天均不得以安装、登录或启用 B 站插件为前提。当前版本尚未启用 B 站跨端联动。

## 已确认的首个群场景（2026-11-02）

后续希望由黄煜斯接手，以 QQ 群机器人打通上下文、反馈整理和桌宠使用流程。用户已确认：

- 指定群的全部新消息作为上下文；群成员 @ 时聊天，识别到 bug 或建议后整理。
- 首版只供黄煜斯使用的测试桌宠查看上下文与反馈。
- 在一台专用电脑上保持吐梨邦 APP 开启；运行机器人和查看反馈的是同一个测试桌宠，先做单机闭环，不需要跨设备同步。

这是模式一优先方向的具体试点，保留模式二已有 DSH 适配。当前 0.1.0 仍只处理主人好友私聊，未实现群聊采集、@ 回复或反馈整理。需求与实施建议见 [群反馈 PRD](../tasks/prd-qq-group-feedback.md)，接手顺序见 [交接说明](group-feedback-handoff.md)。

## 两种模式的区别

| 维度 | 模式一：当前桌宠接入 QQ | 模式二：已有 QQ 宠物接到桌面 |
| --- | --- | --- |
| 面向用户 | 已有桌宠，希望在 QQ 也能找它聊天 | 已有 QQ 宠物，希望保留其积累并增加桌面入口 |
| 会话与记忆由谁管理 | 桌宠宿主 | 原宠物后端及其相关角色、记忆组件 |
| 模型配置在哪里 | 沿用桌宠现有配置 | 沿用原后端的模型配置 |
| QQ 接入 | 插件将 QQ 消息提交到桌宠的同一受控会话 | 按原后端能力适配，保证 QQ 与桌面进入同一会话 |
| 用户是否要另装 DSH | 不需要 | 原后端是 DSH 时复用它；其他后端不因本产品而被强制换成 DSH |
| 主要配置 | QQ 接入地址与凭据、机器人和主人身份、绑定的桌宠 | 原后端连接信息、原宠物/会话映射，以及必要的 QQ 路由配置 |
| 当前实现 | 尚未实现 | 已有 DSH 0.2.1-rc.2 + NapCat OneBot v11 适配，尚无其他后端适配 |

“模型配置”与“原会话”是两件事。仅使用相同模型或相同 API Key，不会自动共享历史、身份和记忆；两个入口必须经过同一套会话管理。

## 后端究竟要装什么

讨论中的“后端”有三个不同层次，应在文档和产品引导中分清：

- **QQ 接入层**：NapCat、SnowLuma 等负责与 QQ 通信，提供收发接口。它们可以接不同机器人框架，不限定使用 DSH。
- **宠物运行与会话层**：DSH、Koishi 上的 AI 插件，或我们的桌宠宿主，负责组织会话、上下文和工具。模式一使用桌宠已有能力；模式二复用外部后端。
- **模型服务层**：实际生成回复的模型服务。运行会话程序不等于在本机下载大模型；采用远程模型服务时，需要相应的模型配置和凭据。

因此，模式一无需另装 DSH，但仍需可用的 QQ 接入环境。安装桌宠、登录 QQ、配置模型和连接外部服务是不同步骤，不能把它们合并成一句“装插件就行”。

## 当前代码边界

截至本次文档更新，0.1.0 只实现了模式二中的一条具体路线：

- 桌面聊天和主人 QQ 私聊进入已有 DSH Session，插件承担业务桥接和来源路由。
- 必须准备正在运行的 DSH 与 NapCat；插件不自动安装或启动 DSH。未部署 DSH 的用户目前不能直接使用这条路线。
- 模型由所连接的 DSH 配置决定；绑定后的主聊天不会改用桌宠本地模型配置。
- 当前连接地址仅接受本机地址；远程服务须先自行转发到本机，不能写成已经实现了远程一键连接。
- 接管前要求停用原桥对目标会话的收发，并确认原人设和记忆在 DSH 可用。第三方桥独立保存的角色、社交状态和记忆尚未自动迁移。
- 已验证真实 Electron、真实 DSH 进程及本地协议测试服务；真实 QQ 登录收发、真实远程部署和非 DSH 后端尚未完成验证。

宿主已集成 Harness 核心组件，可作为模式一的实现基础；这不等于已经向插件开放了 QQ 输入进入主会话的完整能力。现有 `pet.conversation` 绑定接口用于把宿主聊天交给外部提供方，不能把模式二通过的测试当作模式一已完成的证据。

## 后续实施顺序与验收方向

本节是基于已确认目标的实施规划，尚未实现的条目不属于当前版本能力。具体接口、界面和交付版本在实施时细化。

### 第一优先：完成模式一

- 首个实际落地场景为上述群反馈机器人，先按单机试点打通“群聊 → 上下文／反馈 → 同一个测试桌宠”。
- 为 QQ 输入提供宿主受控入口，复用绑定宠物的主会话、人设、模型配置和记忆，避免另建一套互不相通的插件会话。
- 用户可以完成 QQ 配置并开始聊天，全程不要求安装或启动独立 DSH 服务，也不要求填写 DSH 地址或 Session ID。
- 验证“桌面先聊 → QQ 继续 → 桌面接着聊”，以及接入前已有桌宠记忆的延续；不能仅以两端能分别回复作为通过标准。
- 延续来源路由、主人身份绑定、去重、断线处理与重启恢复，隔离不同账号和宠物；解绑 QQ 后保留桌宠原数据和正常聊天能力。
- 没有 B 站插件或未开启联动时，核心能力完整可用。

### 第二优先：补齐模式二的实际接入验收

- 保留现有 DSH 适配并完成真实 QQ 测试环境联调，核实接入前历史、角色和记忆能继续使用。
- 明确原桥共存或接管的方式，防止桌面回复误发 QQ、重复回复，以及遗漏原桥每轮注入的人设/社交上下文。
- 已有非 DSH 宠物按具体后端提供适配；后续支持哪些项目和版本尚未锁定，不承诺所有 OneBot/Koishi AI 插件自动兼容。
- 将原后端配置与桌宠配置分开说明；同一宠物的有效会话来源应明确，切换/解绑不得静默合并或覆盖两份记忆。

### 待实施时细化的事项

- 产品入口建议呈现“让当前桌宠接入 QQ”和“连接已有 QQ 宠物”，优先引导模式一；具体界面仍待设计。
- QQ 接入层的安装辅助范围和各操作系统支持范围尚需细化。群反馈试点已选择专用电脑常开、同机查看；独立云端常驻及跨设备同步不在本期。当前桌宠退出会停止桥接，不能承诺全天在线。
- 模式一所需宿主 SDK、模型调用权限与计费、模式二其他后端的连接协议，以及 B 站可选联动的具体能力，需按各自范围明确后实施。
